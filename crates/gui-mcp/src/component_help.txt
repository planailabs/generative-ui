Generative UI components — write the surface as an HTML string for publish_surface's `html`
field, composing these `<ui-*>` elements:

<ui-heading level="1-3">Title</ui-heading>
<ui-text>Body copy.</ui-text>
<ui-card> ...elements... </ui-card>
<ui-button data-action="act" data-value='{"any":"json"}'>Label</ui-button>
    Clicking sends a backflow event with this action and value.
<ui-input name="field" label="..." placeholder="..." type="text|email|number|...">
<ui-select name="field" label="..."><option value="v">V</option>...</ui-select>
<ui-checkbox name="field" checked>Label</ui-checkbox>
<ui-form data-action="submit_act"> ...inputs... </ui-form>
    Submitting sends one backflow event whose value is { field: value, ... } for all named
    inputs. A submit button is added automatically if you don't include one.
<ui-link to="surface-slug">Label</ui-link>   Navigates to a sibling surface in the deck.
<ui-deck-nav></ui-deck-nav>                  Prev/next navigation chrome for the deck.

Translation note: you may also write ordinary HTML — `<h1>`/`<h2>`/`<h3>`, `<p>`, `<button>`,
`<form>`, `<select>`, and `<a data-to="slug">` are automatically rewritten into the matching
`<ui-*>` components in the browser (so they get styling + backflow wiring). Prefer the `<ui-*>`
components directly; the plain-HTML translation is a convenience.

Templates (faster than writing html): publish_surface `template` + `data_json` renders a
template from slot values; scaffold_deck publishes a whole linked deck of them in one call.
list_templates shows the slots (built-ins: skeleton, form, list, dashboard, partial nav);
save_template stores your own minijinja (Jinja2) template — {% include "nav" %},
{% extends "name" %}, values HTML-escaped, `| tojson` for data-value.

Streaming progress (no republish): emit_stream(surface, name, data_json) appends an event
the browser gets live; its latest value is in the KV view as stream.{name}, so bind it:
  <ui-text><span data-kv="stream.progress.pct">0</span>% — <span data-kv="stream.progress.label"></span></ui-text>
A handler's public host.emit(name, data) streams the same way. Custom JS can listen with
document.addEventListener("ui-stream", e => e.detail /* {surface, name, value} */).

Interaction flows back via wait_for_backflow / list_backflow:
  - a button yields { action, value }
  - a form yields  { action: "<form action>", value: { field: value, ... } }

Handlers (server-side, sandboxed) — publish_surface's `handlers` field
-----------------------------------------------------------------------
Attach code that runs WHEN a backflow action arrives (on by default; server --disable-handlers off).
A handler NEVER edits the surface. It folds the surface's KV view (which the UI reads) and
returns the HTTP response body. Bind a KV value in your HTML with: <span data-kv="key"></span>
(dotted keys allowed: data-kv="user.name"). The UI refreshes bound nodes after each backflow
and on server changes — no page reload.

Each handler entry: { action, lang: "js"|"lua"|"wasm", source (text) or source_base64 (wasm),
  http_allow: ["host"], fs: bool, kv: bool, wall_ms, mem_mb }. Capabilities are default-deny.

Entry point per language (same unified `host` API in all three):
  js   main.js : function handle(event, host) { ...; return body; }
  lua  main.lua: return function(event, host) ...; return body end
  wasm main.wasm: a core module exporting handle(event)->body (see examples/handler-wasm)

Unified host API:
  host.kv.get(key) -> value|null      host.kv.set(key, value)      host.kv.all() -> object
  host.kvPrivate.get/set/all          -- agent-only KV; never served to the browser
  host.http.fetch({url, method?, headers?, body?}) -> {status, headers, body}   (allowlisted)
  host.fs.read(path) / host.fs.write(path, data) / host.fs.list(prefix)  (jailed to state/)
  host.log(level, message)
  host.emit(name, data)               -- record an event the agent picks up (public)
  host.emitPrivate(name, data)        -- agent-only event (not on the public events API)
  host.response(body) or host.response(code, body)   host.responseCode.NOT_FOUND (etc.)
  host.crypto.*                       -- ungated (pure compute, no capability needed):
    .hash(algo, data[, opts]) / .hmac(algo, key, data[, opts]) -> hex   (sha256/384/512/sha1)
    .verifyHmac(algo, key, data, sig[, opts]) -> bool    -- constant-time; webhook signatures
    .randomBytes(n[, enc]) / .uuid()    .encode(data, from, to)   (utf8|hex|base64|base64url)
    .pbkdf2(password, salt, {iterations, length, algo})   .hkdf({ikm, salt?, info?, length, algo})
    .constantTimeEqual(a, b[, enc])
    .aead.seal/open({algo, key, nonce?, plaintext|ciphertext, aad?})   (chacha20poly1305/aes-gcm)
    .ed25519.keypair() / .sign(privKey, data) / .verify(pubKey, data, sig)
    .ecdsa.keypair(curve) / .sign / .verify  (curve p256|p384, ASN.1 DER sigs)
    .x25519.keypair() / .deriveShared(privKey, peerPubKey)   (ECDH shared secret)
    .rsa.sign(pkcs8PrivKey, data, {scheme}) / .verify(derPubKey, data, sig, {scheme})
       (scheme pkcs1-sha256 default | pss-sha512 etc.; bring your own key — ring has no RSA keygen)
    -- bytes cross as strings; opts override per-field/output encoding (<field>Encoding, encoding)

Public vs private: `host.kv`/`host.emit` are visible to the browser (kv.json / events API) and
bound in the UI via data-kv; `host.kvPrivate`/`host.emitPrivate` are for the producing agent
only. The agent reads everything (public + private) via list_backflow / the workspace.

Direct submit (no handler): a surface with no handler for an action still records the event —
a <ui-button data-action="name"> or <ui-form data-action="name"> with its fields IS the event
(name + data). Use this when you don't want a handler; read it via wait_for_backflow.

Example (js): increment a counter and show it via <span data-kv="hits">:
  function handle(event, host) {
    host.kv.set("hits", (host.kv.get("hits") || 0) + 1);
    return { hits: host.kv.get("hits") };
  }
